KEY DECISIONS LOG — SP24 Signal Generator & Analyzer Project
================================================================
(Newest entries at the bottom. Add a dated entry whenever a real decision is made.)

2026-08-06 — Project topic
  Decision : SP24 (Web/Android/iOS app for signal generator and analyzer)
             from the pre-approved list in the course FAQ doc.
  Scope    : (1) Audio waveform generator — square, sine, triangular, chirp,
             sinc, configurable frequency/duty-cycle/amplitude.
             (2) Signal analyzer — time-domain, frequency-domain (FFT), and
             STFT plots of an input signal.
  Source   : Course FAQ doc (docs.google.com/document/d/1Nv5Cd5...), fetched
             2026-08-06 — timeline, evaluation weights, report format, and
             the SP01–SP25 topic list. Original doc link provided first
             (1zu2Ncm...) turned out to require Google auth; FAQ doc was
             fetched instead via the /export?format=txt redirect trick.
  Deadline : Final submission by 20 September (per course FAQ).

2026-08-06 — Tech stack
  Decision : Python throughout — numpy/scipy for the DSP math (FFT, STFT,
             filter design), sounddevice for audio I/O, Streamlit for the UI.
  Why      : Wanted a stack with ready-made signal-processing operations,
             low ramp-up for teammates, and a plausible path to real
             hardware later. numpy/scipy is the standard DSP toolkit;
             a single language avoids a JS/Python split; sounddevice talks
             directly to the sound card (real hardware) and the same
             abstraction can later target other hardware I/O (serial/ADC).
  Rejected : Pure client-side JS (Web Audio API + React) — simplest to
             deploy free, but weaker DSP libraries and no real hardware path.
             Python backend + separate JS frontend — more moving parts and
             deployment complexity than needed for a 3-person course project.

2026-08-06 — Repo ownership split (for 3 people working simultaneously)
  Decision : One repo, three module-owned directories to minimize merge
             conflicts, each owned by one team member working
             independently on its own branch:
               src/generator/   → Person A (waveform synthesis engine)
               src/analyzer/    → Person B (time/freq/STFT analysis engine)
               src/hardware_io/ + app/ → Person C (audio I/O, Streamlit
                                 integration, deployment)
             Shared code lives in src/common/. Each person works on a
             feature/<module> branch and merges to main via PR.
  Why      : Keeps each person editing a disjoint set of files most of the
             time, so simultaneous work rarely collides on the same lines.
             app/ (integration layer) is the one place all three modules
             meet, owned by Person C, merged last.

2026-08-06 — Completed a working reference implementation
  Decision : Built out the scaffold into a genuinely working, verified app
             rather than leaving it as placeholders: all 5 waveforms,
             time/FFT(dB)/STFT analysis, WAV export (Generator) and WAV
             import (Analyzer, so any signal can be analyzed, not just
             what was just generated), in-browser audio playback via
             st.audio, plus the local-only sounddevice page.
  Why      : Needed a working baseline the whole team could run and build
             on immediately, not a skeleton.
  Verified : 16/16 pytest tests pass, including new
             tests/test_app_smoke.py which drives the real multipage app
             via streamlit.testing.v1.AppTest (Home → Generator → Analyzer
             → Live Hardware, checking for zero exceptions and correct
             plot/metric output at each step). Confirmed the running app
             also serves over HTTP. sounddevice hardware I/O itself
             (actual playback/recording) could not be verified on this
             development machine — no audio device present — so that
             still needs a human check on a real machine.
  Caveat   : This is a reference build, not a substitute for the team
             understanding it. Viva is 50% of the grade and requires
             explaining the DSP concepts/implementation individually — see
             the status note at the top of TASKS.md.

2026-09-19 — Deployment target and FFT windowing
  Decision : Deployed to Streamlit Community Cloud (repo already had
             packages.txt/requirements.txt ready for it). Also closed the
             one remaining analyzer gap: FFT windowing (Hann/Hamming vs.
             rectangular), added as a selector on the Analyzer page
             (src/analyzer/freq_domain.py:fft_spectrum's `window` param).
  Why      : Course FAQ deadline is 20 September; hosted deployment lets a
             grader open the app without cloning the repo. The windowing
             gap was flagged from a team status slide cross-checked
             against the actual code.
  Caveat   : The hosted app's viewer access follows the source repo's
             GitHub visibility (private, under the school account) — a
             grader without a Streamlit Cloud login/invite may hit an auth
             wall. Check the app's sharing settings if that's a problem.

2026-09-19 — Video demo via automated Playwright walkthrough, not manual screen recording
  Decision : Wrote a Playwright browser test (tests/e2e/test_demo.py) that
             drives the real running app — cycles every waveform on the
             Generator page, exercises the Analyzer's time/FFT/STFT views
             and the new FFT-window selector, and checks the Live
             Hardware page loads — and records it with Playwright's
             built-in video capture (`--video=on`), run once each against
             a light-theme and a dark-theme Streamlit server
             (--theme.base). Output converted to MP4 via ffmpeg into
             report/video_demo/app_walkthrough_{light,dark}.mp4. A banner
             overlay names each step for ~3s so the recording explains
             itself without narration.
  Why      : Doubles as both an automated regression test and the video
             deliverable, is fully reproducible (tests/e2e/README.md), and
             avoids relying on a human screen-recording session under
             deadline pressure. Reused the same underlying approach (a
             prior project's e2e_tests/ used Selenium + a custom
             ffmpeg/xvfb screen-capture recorder) but simplified it:
             Playwright records video natively, no screen-capture hack
             needed.
  Caveat   : The video does not show live hardware playback/recording
             actually happening — sounddevice needs a real audio device,
             which the automation sandbox doesn't have. Generator page
             audio (st.audio, works everywhere including hosted) IS shown.
             If the live-hardware playback demo is wanted on video, record
             that part separately on a machine with real audio hardware.
